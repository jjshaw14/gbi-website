01

What the site actually is

This is a static site wearing a PHP costume.

All 30 production pages are plain HTML. PHP appears on them for exactly two things — a header.php include and a footer.php include. There is no database, no session state, no mail handler, no login, and no form that posts anywhere. Nothing on this site requires a server runtime.

That single fact decides the platform, the security model, and roughly 90% of the cost. Here is the evidence from the repo:

So the question is not "where do we run PHP." It is "where do we serve 30 HTML pages and 135 MB of images." Those have very different answers and very different price tags.

02

Recommendation

Azure Static Web Apps — Standard tier

≈ $10/month, ≈ $120/year, all-in, including DNS. Global edge delivery, free auto-renewing TLS, per-pull-request preview environments, and a 99.95% SLA.

Static Web Apps is purpose-built for exactly this shape of site, and it deploys from the GitHub Actions workflow the repo already has. The decisive advantage is not price — it is that there is no server runtime to patch. No PHP interpreter, no web server config, no OS image, no CVE feed to track. That eliminates the entire class of risk a WAF would otherwise be compensating for.

Why not App Service with PHP

Running the site "as-is" on App Service sounds like the low-effort path, but it costs more, performs worse, and is not actually as-is:

  • Your .htaccess stops working. Azure App Service on Linux with PHP 8.x serves through nginx, not Apache. site/.htaccess is silently ignored — you lose the gzip rules, the one-year image cache headers, and Options -Indexes and get no error telling you. You would be rewriting that config regardless.
  • Single region, no edge. A B1 instance serves 3.9 MB hero images from one datacenter. You would want Front Door in front anyway, which erases the price difference.
  • You inherit a patch surface for zero benefit — a PHP runtime whose only job is to concatenate two HTML fragments.
  • Defender for App Service then becomes a sensible add-on at ~$15/month, purely to watch a runtime you did not need.

There is a third pattern — Azure Storage static website behind Front Door. It is marginally cheaper on paper but gives up PR preview environments and managed certificates, and adds assembly work. Not worth the trade here.

The bandwidth question

Standard includes 100 GB/month, then charges $0.20/GB. Whether you stay inside that envelope depends entirely on whether you compress the images:

ScenarioPage weight10k visits/moOverage
Images as they ship today~4.0 MB~100 GBAt the cap
After WebP/AVIF + resize~0.4 MB~10 GB$0.00

The repo carries 516 images totalling 135 MB, with seven hero images between 3.5 MB and 3.9 MB each. Converting them to WebP or AVIF at sensible dimensions typically cuts that by 8–10×. That one change keeps you inside the included bandwidth indefinitely, drops the deployed app from 136 MB to roughly 15–20 MB, and will do more for real-world page speed than any infrastructure choice on this page.

Static Web Apps caps app size at 500 MB on Standard (250 MB on Free). At 136 MB you fit comfortably today, but each new case study adds gallery images — compressing now buys years of headroom.

If you want to try Free tier first

The Free tier ($0) would technically host this site — 100 GB bandwidth, 250 MB app size, custom domains, managed TLS. It has no SLA and only 2 custom domains. For a company's primary web presence, $9/month for a 99.95% SLA and staging environments is the right call, but Free is a legitimate way to validate the deployment before committing.

04

Security — spend proportional to the attack surface

A WAF blocks SQL injection, command injection, path traversal, and server-side XSS. This site has no SQL, no command execution, no filesystem reads from user input, and no server to inject into. A managed WAF in front of it is $4,000/year of protection against attacks that have no target.

That is not an argument against security spending — it is an argument for putting it where the real exposure is. For a static marketing site, the genuine risks are these, and the mitigations are almost all free configuration:

Real riskMitigationCost
Defacement via compromised deploy pipelineOIDC federated credentials instead of long-lived publish-profile secrets; branch protection + required review on main; environment approval gate$0
Supply chain — third-party scriptsAdd SRI hashes to the d3 and topojson tags, or self-host them. Currently neither.$0
Clickjacking, MIME sniffing, mixed contentSecurity headers via globalHeaders in staticwebapp.config.json — CSP, HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy$0

On code and vulnerability scanning

Worth knowing before anyone quotes you for it: this repo has no dependency manifest of any kind — no npm, no Composer, no lockfile. Software Composition Analysis has literally nothing to analyse, and SAST has no server-side code to walk. GitHub Advanced Security at roughly $30–49 per committer per month would return very little here.

What is worth turning on, all free or near-free: Dependabot (for GitHub Actions versions), secret scanning with push protection, and CodeQL for JavaScript — which would at least cover site.js and projects-map.js. Revisit paid SAST if the site ever grows a real backend.

If a WAF is non-negotiable

Industrial and energy customers increasingly send security questionnaires that ask "is your public web presence behind a WAF?" as a yes/no. If GBI needs to answer yes, the honest options are:

  • Front Door Standard + custom rules — ~$530/year. Gives you rate limiting, geo-filtering, and IP restrictions. Does not include Microsoft-managed OWASP rulesets. One caveat: without Private Link (a Premium feature) the Static Web Apps default hostname stays directly reachable, so the WAF can be bypassed by anyone who finds it.
  • Front Door Premium — ~$4,140/year. Managed OWASP rulesets, bot protection, and Private Link to lock the origin so traffic must pass the WAF. This is the configuration that survives an auditor's follow-up question.

My read: unless a contract or an insurer requires it in writing, put the $4,000 somewhere it buys more — and note that "static hosting with no server-side execution" is a stronger answer to most questionnaires than "PHP behind a WAF."

05

Punch list before cutover

The Static Web Apps path in this repo is not deployable today. I ran scripts/build-static.py against site/ and checked the output — these are ordered by what blocks the launch.

  1. Build script drops the site navigation Blocker

    build-static.py inlines only the footer include. Every page also has a header.php include carrying the entire top nav, plus a feedback-widget.php include. I confirmed it: all 33 generated HTML files still contain raw <?php>. Deploy this as-is and every page ships with no navigation. The script needs to handle the header include and its $NAV_ACTIVE variable.

  2. Review tooling must be excluded from the build Blocker

    feedback.php, fb-board.php, feedback-widget.php, feedback-test.php and tag-review.php accept unauthenticated file uploads and write to disk, gated only by a hardcoded cookie token ('review-access'). Inert on a static host, but they should not be published at all — add them to a skip list alongside partials/, and strip the widget include from every page.

  3. 404 handling is contradictory and the page does not exist Fix

    The generated staticwebapp.config.json declares responseOverrides.404 → /404.html, but no 404 page exists in the repo. It also sets navigationFallback to rewrite unmatched routes to /index.html, which serves the homepage with a 200 for every bad URL — poor for users and actively harmful for SEO. Pick one behaviour, and author the 404 page.

  4. Compress the image library Fix

    516 images, 135 MB. Ten are over 2 MB; project-oge.jpg, project-ipa-kiewit.jpg and hero-smp.jpg are 3.9 MB each. Convert to WebP/AVIF and resize to display dimensions. Biggest single win available — for page speed, bandwidth cost, and app-size headroom.

  5. Add SRI to the CDN scripts Fix

    site/projects/index.php:538-539 loads d3 7.8.5 and topojson 3.0.2 from cdnjs with no integrity attribute. If cdnjs is ever compromised, that is arbitrary script execution on your domain. Add SRI hashes or vendor the two files locally — this is the one genuine vulnerability I found in the codebase.

  6. Port the .htaccess rules Fix

    Neither Azure path reads .htaccess — Static Web Apps uses staticwebapp.config.json, and Linux App Service on PHP 8 uses nginx. Move the cache headers and compression rules across, and set the security headers from section 04 at the same time. The current config only sets cache-control: must-revalidate globally, which would defeat the one-year asset caching you have today.

  7. Decide the contact form Decision

    It currently renders a full project-inquiry form that silently discards everything typed into it. That is worse than having no form — a prospect fills it in and hears nothing back. Either wire it to an endpoint (Azure Function with an email relay, or an embedded form service) or replace it with the mailto: contacts already on the page. This is a business decision, not a technical one, but it should not survive launch.

  8. Switch deploy auth to OIDC Hardening

    Both workflows use long-lived credentials — a publish profile for App Service, a static API token for Static Web Apps. Azure federated credentials let GitHub Actions authenticate with short-lived tokens and no stored secret. Worth doing at provisioning time rather than retrofitting.

  9. Minor — build script crashes on Windows Hardening

    The closing print() emits an emoji and raises UnicodeEncodeError under the cp1252 console encoding, after the build has already written its output. Harmless in GitHub Actions on Ubuntu, confusing when run locally on Windows.

06

Provisioning order

  • Resource group — e.g. rg-gbi-web-prod, tagged for cost tracking.
  • Static Web App, Standard tier, region closest to your users (West US 2 or Central US). Content is edge-distributed regardless; the region only sets the management plane.
  • Fix punch-list items 1–3, then deploy to a staging environment and verify navigation renders on every page.
  • Custom domain — validate mygbi.com and www, let Azure issue managed certificates, confirm HTTPS redirect.
  • Azure DNS zone, then cut the registrar nameservers over once records are verified. Keep Cloudways live until this resolves cleanly.
  • Harden — OIDC deploy credentials, security headers, branch protection, resource locks on the DNS zone.
  • Enable Defender for Cloud foundational CSPM and review the secure score.
  • Decommission Cloudways after a week of clean traffic, and remove the stale SFTP credentials in deploy.config.
